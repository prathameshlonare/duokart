Resilient Multi-Tier Cloud Architecture

A small-shop order engine engineered on AWS across two Availability Zones. Decoupled via asynchronous queues and automated self-healing to prevent lost orders and isolate database failures during festival traffic rushes.

System Overview

What Was Built

A multi-tier retail order and billing backend on AWS. An internet-facing Application Load Balancer routes traffic to private EC2 instances (Auto Scaling Group) across two Availability Zones. Backed by private Multi-AZ RDS MySQL, direct S3 uploads, and SQS/Lambda asynchronous order decoupling.

Primary Goal Zero Lost Orders
High Availability 2 Availability Zones

End-to-End System Architecture

Requests enter via an internet-facing Application Load Balancer and terminate at private compute nodes. Relational persistence, file storage, and asynchronous processing are segregated into distinct security groups and fault domains.

AWS Architecture Map: us-east-2 (Ohio)
Tier 1: Ingress

Public Load Balancing

Internet-facing ALB spans Public Subnet 1 (2a) and Public Subnet 2 (2b). Absorbs traffic surges and health-checks backend instances on port 5000 via /health.

Port 80 Inbound → Port 5000 Backend
Tier 2: Compute

Private Auto Scaling Group

EC2 instances run in private subnets with zero public IPs. Inbound traffic allowed strictly from ALB security group. Outbound internet egress routed through a single NAT Gateway.

Min: 2, Max: 4 (t3.micro, Ubuntu 24.04)
Tier 3: Persistence

Multi-AZ RDS MySQL 8.0

Stores catalog and relational orders. Automatic synchronous standby in AZ-2b. Port 3306 locked down exclusively to compute security group; public accessibility disabled.

Synchronous Standby Failover
Tier 4: Asynchronous

SQS Queue & Lambda Worker

Orders decouple into SQS Standard returning immediate HTTP 202. Dead-Letter Queue catches poison orders after 3 retries. Lambda worker performs conditional DynamoDB writes.

DLQ Redrive (maxReceiveCount: 3)

Subsystem Isolation Specifications

Configuration parameters, security group bindings, and failure protections declared in CloudFormation.

Eight Alarms, One Mailbox

Configured in CloudWatch to alert via SNS before buyers notice latency or failures. Three alarms indicate “Insufficient Data” during normal steady-state operations, signifying zero errors rather than broken instrumentation.

Alarm Metric Trigger Criteria Operational Rationale Healthy State
alb-5xx 5xx > 10 / 5 min Flask 500 errors occur only on unhandled server exceptions or application crashes. Active (OK)
alb-unhealthy unhealthy > 0 for 2 min Provides an early warning buffer before Auto Scaling instance replacement completes. Active (OK)
rds-cpu CPU > 80% × 3 db.t3.micro is a burstable instance; sustained 80% utilization signals a query bottleneck or memory leak. Active (OK)
rds-storage free < 5 GB Early warning on 20 GB gp2 allocation, triggering storage auto-scale before disk exhaustion. Active (OK)
sqs-age oldest > 300 s Catches worker lag if an order sits unserved in the ingestion queue for over 5 minutes. Active (OK)
dlq-depth visible ≥ 1 Any poison or unparseable payload moved to Dead-Letter Queue immediately pages on-call. 0 (Insufficient)
worker-errors errors > 0 Lambda worker execution failure: bad schema, SNS publish deny, or DynamoDB write rejection. 0 (Insufficient)
ddb-throttle throttles > 0 Signals a hot orderId partition write spike exceeding provisioned capacity. 0 (Insufficient)
